# CareSaath — Production Runbook

This is the operational checklist for the backend deployed on Render. It covers
the gaps that code alone cannot close: backups, alerting, vendor credentials and
incident response.

---

## 1. Go-live checklist

- [ ] `CORS_ORIGINS` set to the real frontend origins (comma-separated)
- [ ] `SWAGGER_ENABLED=false` (default in production; docs are not public)
- [ ] `SMS_API_URL` + `SMS_API_KEY` set, and a real OTP delivered to a test phone
- [ ] All three encryption keys generated by Render (not `change-me` / `caresaath-dev-*`)
- [ ] `PAYMENT_WEBHOOK_SECRET` (and provider-specific secrets) set
- [ ] `SMTP_HOST`/`SMTP_USERNAME`/`SMTP_PASSWORD` set and a test email delivered
- [ ] `TURN_URLS` + `TURN_SHARED_SECRET` set (calls behind NAT)
- [ ] `PAYMENT_CHECKOUT_BASE_URL` set if JazzCash/Easypaisa are offered
- [ ] First admin provisioned with `npm run admin:create`
- [ ] Commission rates exist for every specialty (`SELECT * FROM "CommissionRate"`)
- [ ] Production database is **not** the demo-seeded database
- [ ] `/health/ready` returns 200 from outside Render
- [ ] Database backups/PITR enabled and a restore has been tested
- [ ] Uptime monitor + error tracking + log drain configured
- [ ] `prisma migrate deploy` reviewed; a pre-migration snapshot exists

---

## 2. Health and readiness

| Endpoint | Purpose | Expected |
|---|---|---|
| `GET /health` | Liveness — process is accepting requests | `200 {"status":"ok"}` |
| `GET /health/ready` | Readiness — Postgres + Redis reachable | `200 {"status":"ok","checks":{...}}`, else `503` |

Render uses `/health/ready` as the deploy health check. A failing dependency
therefore keeps the previous release live instead of routing traffic to a broken
instance.

---

## 3. Backups and restore

1. Enable Render PostgreSQL backups / point-in-time recovery on the database plan.
2. Take a manual snapshot **before** every release that contains a migration.
3. Test a restore quarterly into a scratch database:
   - restore the snapshot
   - run `npx prisma migrate deploy --config prisma7.config.ts`
   - boot the API against it and hit `/health/ready`
4. Record RPO/RTO. Suggested pilot targets: RPO ≤ 24 h (or PITR), RTO ≤ 2 h.
5. Redis is ephemeral by design (OTP, cache, rate limits, chat upload sessions).
   Do not treat it as a system of record.

---

## 4. Monitoring and alerting

Minimum signals:

- **Uptime**: external probe on `/health/ready` every 1–5 minutes, alert after 2 failures
- **Errors**: error tracker (Sentry or equivalent) wired into `AllExceptionsFilter`
- **Logs**: Render log drain to a searchable store; every request has `X-Request-Id`
- **Latency**: p95 for `/api/v1/caregivers` (search) and booking writes
- **Business**: payment webhook failures, OTP send failures, SOS events
- **Infrastructure**: Postgres connections, Redis memory, 5xx rate

Alerts should page for: readiness down, 5xx spike, webhook failures, SOS.

---

## 5. Security operations

- Rotate `JWT_*`, encryption and webhook secrets on a schedule; changing an
  encryption key requires re-encrypting existing rows first.
- Keep `SWAGGER_ENABLED=false` in production.
- Keep `CORS_ORIGINS` to known browser origins only.
- The per-IP rate limiter is a floor, not a substitute for the per-phone OTP
  limits in `AuthService`.
- Review admin accounts monthly; remove leavers immediately.
- Do not enable `SMS_DEV_LOG=true` in production (it writes OTPs to logs).

---

## 6. Payments

- **Cash** and **Stripe** are the implemented methods.
- JazzCash/Easypaisa need a real merchant integration and a real
  `PAYMENT_CHECKOUT_BASE_URL`; the placeholder host does not process payments.
- Webhooks are idempotent and fail closed when a secret is configured.
- Reconcile gateway settlements against `Payment` rows daily.

---

## 7. Incident response

1. Confirm scope with `/health/ready`, Render events and the error tracker.
2. If a release caused it, roll back to the previous Render deploy (the
   pre-deploy migration must be backward-compatible; prefer additive migrations).
3. If the database is involved, stop writes, restore from snapshot/PITR, then
   replay any queued webhooks.
4. Communicate to affected users; preserve audit logs and request IDs.
5. Write a short post-incident note: timeline, impact, root cause, follow-ups.

---

## 8. Deployment process

- `render.yaml` deploys from `main`; `autoDeploy` is on.
- Keep `dev` for integration; merge to `main` only through a reviewed PR.
- Every release: CI (lint, build, unit, e2e) green → snapshot → deploy →
  verify `/health/ready` → smoke-test OTP, search and a cash payment.
